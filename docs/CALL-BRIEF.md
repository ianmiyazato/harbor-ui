# Call brief: Harbor UI

For Ian, before the call with the founding team that asked for frontend and design evidence.
Every number here comes from a real run on 2026-09-28. Links are at the end.

## 1. What they're really asking

- **Can you make product and design decisions, not just implement?** They want to hear trade-offs
  you chose and why, including the ones that cost you something.
- **Do you have taste and care for detail?** Hover, focus, loading, error and motion are where they
  will judge it, not in a hero section.
- **Can you build the frontend foundation a small team will live on?** Tokens, components, tests and
  budgets that let three engineers ship consistent UI without a designer on every PR.

## 2. The 80/20: five points that carry the call

1. **Tokens are the API.**
   - Say: "Components can only read semantic tokens, and a theme is just a different mapping of the
     same names, so one person can restyle every product safely."
   - Show: [Button page](https://harbor-ui-docs.vercel.app/components/button), then flip the demo's
     theme toggle: Light, Dark, High contrast.
   - Number: **127 semantic tokens** (206 in total), 3 themes, one set of names.
2. **Accessibility is measured.**
   - Say: "Contrast isn't a claim in a README. CI computes it for every pair the components render,
     in every theme, and fails the build below WCAG."
   - Show: [Foundations → Color → Contrast report](https://harbor-ui-docs.vercel.app/foundations/color#contrast).
   - Number: **39 pairs × 3 themes = 117 checks, 100% passing.**
3. **States before variants.**
   - Say: "Hover, focus, loading and error are where products feel cheap or polished. Every state
     comes from one registry, so the docs, the axe tests and the screenshots can't drift apart."
   - Show: the Button states row, then the Loading switch: the button keeps its exact width.
   - Number: **49 documented states** across 12 components, each checked by axe and screenshotted
     in 3 themes.
4. **Motion as a system.**
   - Say: "Every animation has a spec, a reduced-motion design, and moves only transform and
     opacity, so it never shifts layout."
   - Show: [Lab](https://harbor-ui-docs.vercel.app/lab), Drag to reorder with _Slow motion ×5_
     on, then _Reduced motion_ on and Replay.
   - Number: **CLS 0** on every interaction (tested), **0 frames over 50 ms** unthrottled; the
     worst frame at 4× CPU throttling was 66.7 ms, at the view-transition capture.
5. **Test-first, small surface, deep quality.**
   - Say: "Every behavior started as a failing test committed before the code, and the history
     proves it. Budgets and coverage gates run in CI."
   - Show: the repo's commit history (`test(button)…` then `feat(button)…`), the coverage line in
     the README, `.size-limit.json`.
   - Number: **519 automated tests**, **97.74%** statement coverage on components (100% on
     tokens), a Button import is **0.64 kB gzip**.

## 3. A 60-second opening

"Most of my work has been backend and distributed systems, so I built this the way I'd build a
service. Tokens are the contract: components depend on names, never on values, the same way
services depend on an interface rather than an implementation. Reliability is tests and budgets:
519 automated tests, contrast computed in CI, and size budgets that fail the build. Failure
handling carries over too. The like button updates optimistically and rolls back with a retry when
the request fails, and every widget has a fallback: no View Transitions API means a crossfade, and
reduced motion means an instant swap. I scoped it on purpose: twelve components, not sixty, with
every state done properly. Can I show you two screens, and then you tell me where you'd like to
go deeper?"

## 4. A 5-minute demo path (six clicks)

1. **Home** ([link](https://harbor-ui-docs.vercel.app)): "One line of pitch, then the three ideas
   as live tiles. Everything here is static HTML: content pages load no JavaScript files."
2. **Components → Button**: "Same states, three themes: watch the toggle re-theme only the
   demo. These three accessibility facts come from test data, and the target size is measured in
   the browser."
3. **Foundations → Color, scroll to Contrast report**: "117 checks, generated by the token tests.
   If someone changes a color and breaks 4.5:1, CI goes red before anyone sees it."
4. **Foundations → Motion, press Play on _deliberate_**: "Every duration has a reduced
   counterpart right next to it. Springs are simulated once and compiled to CSS."
5. **Lab**: tick _Next request fails_ and press Like: "Optimistic update, then a rollback with a
   shake and a retry." Then Drag to reorder with the keyboard: Space, arrow down twice, Space.
   Then Card to detail: "View Transitions, with a crossfade fallback."
6. **GitHub history** ([commits](https://github.com/ianmiyazato/harbor-ui/commits/develop)):
   "Each feature is a test commit, then a feat commit. Two bugs were caught by later tests: axe
   flagged a disabled switch's description, and the lab's Playwright tests caught a Checkbox hit
   target."

Stop after three screens and ask what they want to see.

## 5. How this maps to their company

A shared token layer lets a small team ship consistent UI across several products and markets
without forking styles. Design quality is most visible where talent and brands meet the product,
which is exactly the states, motion and accessibility work shown here. The same system would power
a talent page or a campaign dashboard from day one, themed per brand by swapping token mappings.

## 6. Likely questions, with crisp answers

- **Why not build every primitive yourself?** "Focus traps, typeahead and screen-reader behavior
  are solved problems with long tails. Radix handles the behavior; I own the API, tokens, states and
  motion. The cost is size: the full package is 45 kB gzip against a 35 kB target, and I wrote that
  down as a known gap instead of hand-rolling a worse Select."
- **How would you scale this to a team of 10?** "Keep the rules in the tools, not in a wiki:
  stylelint for token-only CSS, the contrast matrix, per-usage size budgets and visual baselines on
  PRs into main. Add CODEOWNERS for the tokens package, a changeset per PR, and a design review step
  for new semantic tokens, since those are API changes."
- **How do you keep design and code in sync?** "Tokens are the single source: they emit CSS, a
  typed module and JSON a design tool can import. The docs page for each component is generated from
  the same states registry the tests use, so what design reviews is what ships."
- **What would you do differently?** "Measure the React runtime earlier. It's 65.9 kB gzip, so the
  lab's 60 kB page budget was unreachable from day one. I kept React because the demos must prove
  the real components, but I'd set that budget with the runtime in view. I'd also install the Vercel
  GitHub integration so deploys trigger from Git rather than an API call."
- **How long did this take?** "One focused day: the first commit was at 05:07 and v1.0.0 at 11:46
  on 28 September, across 39 pull requests. I built it for this conversation and scoped it
  deliberately. I wrote the plan and the constraints, and I paired with Claude Code on the
  implementation, test-first. You'll see it credited in the commits. The decisions and trade-offs
  are mine, and they're in the decision log."

## 7. What not to do

- Don't oversell it as production work: it's a deliberate, well-tested concept built for this
  conversation.
- Don't recite every component; pick Button, the contrast report and one lab interaction.
- Don't show more than three screens before asking what they want to see.
